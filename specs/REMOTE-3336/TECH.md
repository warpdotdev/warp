# Environment Git Mirror Cache — Technical Spec

Tracking issue: [REMOTE-3336](https://linear.app/warpdotdev/issue/REMOTE-3336/cache-environment-git-clones-on-warp-build-cache-root-via-a-typed).

## Summary
Reuse the Namespace build-cache volume to accelerate structured environment repository checkouts. A hidden, one-shot Warp/Oz CLI command owns the Git operations on Linux, macOS, and Windows, including uncached runs. A cache failure must not make an otherwise valid checkout fail. A prerequisite PR first teaches Warp to write Namespace metadata for existing build caches; the mirror implementation adds Git usage to that same writer.

## Behavior
1. On a Linux or macOS Namespace run with a usable `WARP_BUILD_CACHE_ROOT`, each distinct structured source repository has a full-object bare mirror under `git-mirrors/<stable-key>`. A cold run populates it from the canonical forge URL before checkout. A warm run refreshes it before checkout; it never serves an unchecked stale branch tip. Mirror operations do not use `--filter=blob:none`.
2. Every new cache-backed working checkout has all reachable Git objects for its fetched refs and remains independent of the mirror after preparation. Its `origin` points to the canonical forge URL, no `objects/info/alternates` file points into the cache, and Git does not need to lazily fetch blobs for that history.
3. An unset cache root, a non-Namespace run, Windows (which has no attached build-cache volume today), an unwritable volume, or a failed mirror operation uses the existing blobless network-clone behavior. A missing or damaged mirror may first be populated or rebuilt; if that fails, checkout proceeds directly from the forge. A failed direct clone, fetch, or checkout remains a fatal environment setup error.
4. The same typed helper handles every structured clone on Linux, macOS, and Windows, even without a cache. Existing directory handling, SHA/ref pinning, `fetch_branch_only` substitution, parallel repositories, per-repository failure attribution, diagnostic output, resolved-HEAD snapshots, codebase indexing, and post-setup origin removal keep their existing behavior. Per-repository lifecycle progress appears as workers start, fall back, and finish; it does not wait for the entire batch.
5. Git authentication continues through the session's credential helper. Neither the mirror's remote URL nor its key, metadata, command arguments, and diagnostics contain credential material. Mirror state remains scoped to the existing server-derived build-cache tag.
6. On a cache-enabled run, one metadata write records a complete snapshot of successful build-cache mounts and, if present, `git-mirrors` for this instance. Entries inherited from a prior instance are not retained unless this instance uses those paths. Metadata failure is non-fatal and does not affect checkout correctness.
7. The Factory-definition repository clone remains the existing setup command. This feature changes only structured environment repositories.

## Technical design
### Typed checkout command
- Add a hidden `environment-checkout` CLI command to `CliCommand` in `crates/warp_cli/src/lib.rs`. Define `--requests-file <path>` and `--failure-report <path>` in `crates/warp_cli/src/environment_checkout.rs`. Dispatch it without login, run ID, or server API initialization in `app/src/ai/agent_sdk/mod.rs`; make the command one-shot on Linux, macOS, and Windows. Update exhaustive CLI tracing/telemetry matches without recording repository names or URLs.
- The driver writes validated `RepositoryCloneRequest` values to a private temporary **JSON file**. Include forge, owner, repository, checkout name, head kind/value, `fetch_branch_only`, and working directory. Do not add a protocol version: driver and helper run from the same binary. Do not serialize credentials or arbitrary clone URLs. The helper reconstructs the URL with `SourceRepo::https_clone_url()`. Shell-quote the executable and file paths for Bash, Zsh, Fish, or PowerShell; do not embed the JSON in terminal command text. Reject malformed JSON, unsupported forges, invalid repository identities, and duplicate checkout targets before starting work. Delete the request file after the helper exits, including on failure.
- Resolve the executable from the running Warp/Oz process, not an unverified `warp` in `PATH`. Invoke it through the active session's `TerminalDriver::execute_command`, so Git inherits the session's home and credential store. The requester has confirmed that driver and session share a filesystem, including for the report file. If the executable is not reachable or the helper cannot start, report a clear setup failure; do not silently run the old shell script. Cover Linux container, macOS app-bundle, and Windows executable paths.
- Move both single-repo and parallel-repo Git logic from `environment.rs` into a small app-owned module with typed request and Git-process adapters. Do not invoke `sh -c` for Windows checkout paths. Use a bounded worker pool for distinct repositories; only one worker may update any one stable mirror key per batch. Emit short, sanitized per-repository lifecycle lines to the visible terminal command as each worker starts, begins a cache fallback, and finishes; serialize those writes so lines do not interleave. Buffer Git child output per repository for bounded/redacted diagnostics in request order; do not build a raw Git-output multiplexer. Return a typed per-repository failure report in the private temporary directory; the driver reads it directly with `std::fs` after the helper exits and removes it. If the file cannot be read, attribute the failure to the batch. Preserve the existing `PrepareEnvironmentError` clone/checkout categories, output redaction/truncation, and credential-identity diagnostics. Do not put raw tokens or a credential-bearing URL in the report.
- Keep request preparation, `SetupStep::EnvironmentRepoClone`, resolved-HEAD snapshot capture, index registration, build-cache setup, setup commands, and origin removal in the current order. The helper only materializes repositories; it does not own environment-wide setup.

### Mirror lifecycle
- Add one function that resolves an optional Git-mirror root. It checks Linux/macOS Namespace isolation, the cache-root environment variable, and an accessible writable directory. Windows uses the same typed helper without a mirror until a Windows cache volume is attached and validated in a separate change. The remainder of the checkout code accepts `Option<&Path>`; changing to a separate volume later changes only root resolution. Never write to `repos/` or `shared/`.
- Compute `<stable-key>` from the canonical forge host, owner, and repository with `RepoIdentity`/`RepoCacheKey`; key the **source** repository after any `clone_from` substitution. The hash excludes refs, checkout paths, user IDs, and secrets. Reject path traversal and symlink escapes under `git-mirrors/`. Cache reuse is confined to the server-scoped volume.
- For an absent mirror, initialize a bare repository directly at its validated cache key and fetch complete branch/tag objects from the canonical HTTPS forge URL without `--filter`. For an existing mirror, verify that it is bare, has the expected credential-free origin, and has no promisor/filter configuration; fetch/prune before use. If it is invalid, remove only that managed mirror path (never follow a symlink) and rebuild it in place. If a fetch or rebuild fails, do not serve the old mirror: use a direct network clone. A temporary sibling mirror is not required. A partial directory can be detected on the next run, and Git updates fetched refs transactionally; per-batch serialization prevents one helper from racing its own mirror updates.
- Seed each new cache-backed checkout using the full mirror as a reference while retaining the canonical forge URL as `origin`. Fetch requested refs from the forge when the existing semantics require it, then detach to freshly fetched `FETCH_HEAD`; do not resolve from a stale local branch. Do not pass `--filter` on this path. For `fetch_branch_only`, preserve the default-branch alias and single-branch fetch refspec. A pinned object absent from mirror refs must be fetched from the forge without a filter. For an existing target, preserve today's skip/fetch behavior without replacing the directory or reading unrelated cache objects.
- Use Git's `--dissociate` option for cache-backed clones so the working checkout does not retain mirror alternates. Do not scan blobs or check for alternates at runtime after a successful Git command; tests verify those guarantees. If a cache-backed attempt fails before a new checkout is complete, remove only its newly created target and retry once directly from the forge. All uncached and fallback network clones/fetches retain today's `--filter=blob:none` behavior, including lazy blob fetching. A failed direct attempt is fatal; do not delete or overwrite a pre-existing target.
- Emit bounded categories for cache hit, cold population, invalid/rebuilt mirror, cache failure with network fallback, and fatal direct checkout. Do not log raw cache paths, remotes, credentials, or the serialized batch. Do not add cross-run `flock`: Namespace instances receive private forks of the CACHE volume.

### Namespace usage metadata: prerequisite PR first
- **Before mirror implementation, land the separate prerequisite PR** for current build-cache usage metadata. Add `cache_path` and `mount_path` to `crates/build_cache/src/spacectl.rs::Mount`. In `crates/build_cache/src/lib.rs`, collect successful mount paths into a `CacheSetupReport` field directly from the real-mount loop; the loop already knows it is not a dry run. Dry-run detections and failed mounts contribute no paths. Convert those results to a `build_cache`-owned usage record or iterator containing the volume-relative path, mode, and actual mount target. Pass it to the reusable writer in `crates/build_cache/src/metadata.rs`; do not import or accept `spacectl::Mount` in that module. A successful path entry has `source: "warp"`, `cacheFramework: <spacectl mode>` and `mountTarget: [<actual mount target>]`; if one cache path has multiple modes or an empty mode, omit `cacheFramework` and union/sort its targets. The writer also accepts optional additional entries; the prerequisite initially passes none. It must be usable when no build-cache modes were detected.
- In the mirror implementation, add the single volume-relative `git-mirrors` entry to the same in-memory snapshot, only if the mirror directory exists. Its fields are `source: "warp"`, `cacheFramework: "git"`, and `mountTarget: []` (working checkouts are independent copies). The helper creates the directory during checkout, before the later metadata write. Have `app/src/ai/agent_sdk/driver/cache_setup.rs::setup_caches` collect all successful mounts, include optional Git usage, and invoke the writer **once after all mounts and before user setup commands**, even if some mount invocations degraded. Do not add a second metadata-writing path in `environment.rs`.
- Emit one complete `CacheMetadata` version 1 snapshot with canonical protobuf JSON field names: `version`, UTC `updatedAt`, and `userRequest`. Keys are paths relative to `<WARP_BUILD_CACHE_ROOT>`, not absolute paths. The snapshot contains only usage recorded for this instance; do not read, validate, or merge an existing metadata file, regardless of its field spellings, contents, or version. Create `.ns` if absent; reject an existing `.ns` symlink rather than following it. Write the new document to a `tempfile::NamedTempFile` in `.ns`, with owner-only permissions on Unix. Finish writing before persisting it over the final metadata path; rely on the temporary file to generate a unique name and clean up on failure. Persist by pathname with atomic replacement on the same filesystem; never open an existing final-component symlink or FIFO or follow a symlink target. A final-component symlink or FIFO is replaced by the regular metadata file without reading its contents. Pathname-based persistence does **not** protect against a concurrent swap of the parent directory; do not add `cap_std` for this writer. A write failure is non-fatal. Do not write metadata when caching is disabled.
- No `warp-server` change or new Namespace volume is required. Namespace reads this one file to report build-cache and Git-mirror path utilization. Verify both categories in a staging report before rollout.

## Decisions
- **Volume:** Reuse `WARP_BUILD_CACHE_ROOT/git-mirrors/` now. A dedicated `NSC_GIT_MIRROR` volume isolates capacity but adds provisioning and tagging work; one optional-root function preserves that later option. Approved by the requester.
- **Checkout engine:** Move every structured environment checkout into the hidden typed helper. Keeping the shell code for uncached runs would create two implementations of ref and failure semantics; the broader migration needs regression coverage. Approved by the requester.
- **Payload transport:** Use a temporary JSON request file rather than base64-encoded JSON in an argument or repeated per-repository flags. It preserves a readable typed schema, avoids command-line length/quoting issues on Windows, and keeps repository names out of visible command text; it requires a private file and cleanup. The requester confirmed shared filesystem access.
- **Progress:** Emit immediate lifecycle messages for each worker, but keep raw Git output buffered for redacted diagnostics. Streaming raw child output needs a concurrent multiplexer and may expose credential-bearing Git errors; lifecycle messages provide incremental status without that risk.
- **Mirror completeness and recovery:** Cache all reachable blobs, accepting more initial transfer and cache capacity than a blobless mirror in exchange for avoiding later lazy fetches. Create/rebuild in place and validate before use; a temporary sibling would hide partially written mirrors, but validation plus direct-network fallback handles interrupted population without duplicating large mirror data.
- **Runtime verification:** Trust Git's successful fetch and `--dissociate` behavior instead of scanning blobs or checking alternates for each checkout. Keep automated tests for full blobs and independence.
- **Freshness and failure:** Populate cold mirrors, refresh warm mirrors, and fall back to direct network fetch/clone after a cache failure. Serving stale refs saves network calls but violates requested pin/default-branch behavior. Approved by the requester.
- **Helper failure:** Fail clearly when the executable itself cannot run. Falling back to the old shell snippet would retain an untested, divergent engine; only cache problems fall back to network Git. Approved by the requester.
- **Capacity:** Write Namespace `CacheMetadata` instead of a bespoke disk-usage counter. This allows Namespace to report path utilization from the shared 20 GiB volume. The requester asked for this change; eviction and resizing remain separate work.
- **Metadata sequencing:** Upstream `spacectl` 0.12.2 does not write the metadata file. A separate prerequisite PR writes existing build-cache entries once; this feature supplies a Git entry to the same writer. Writing Git metadata alone first would leave existing build-cache usage unattributed.
- **Metadata snapshot and replacement:** Overwrite inherited metadata with this instance's complete usage snapshot rather than merging prior entries. Merging preserves third-party fields but can report paths this instance never used and requires parsing untrusted inherited JSON. Use `tempfile::NamedTempFile` in the metadata directory and persist by pathname rather than adding a `cap_std` directory handle; the existing `tempfile` dependency supplies unique naming, cleanup, and atomic replacement. Pathname operations cannot guarantee safety if the parent directory is swapped concurrently; the requester accepts that risk.
- **Factory definition:** Keep its credential-bearing setup-command clone out of this batch. Integrating it needs a distinct secret-safe input and compatibility path for persisted environment commands. This exclusion was approved by the requester.

## Assumptions
- `source: "warp"`, `cacheFramework: "git"`, and an empty `mountTarget` represent an unmounted mirror directory under the published `CachePathUsage` schema. Confirm the path appears under Namespace's path-utilization report during staging validation; if Namespace rejects this representation, revise the spec before rollout.
- Assumption: this instance is the sole owner of its metadata snapshot. Namespace forks cache volumes per instance, so a cross-instance lock and inherited third-party entries are not required for this write.

## Out of scope
- A dedicated Git-mirror volume, cache-size increase, mirror eviction policy, and performance guarantee. Namespace may return older generations or reset an oversized cache; observed usage and measured clone timings should inform later changes.
- Caching the Factory-definition setup command, arbitrary user setup-command clones, Git LFS objects, and recursive submodules. These are separate clone flows or optional Git features, not structured environment repositories.
- Windows mirror caching is deferred because the current Namespace worker does not attach `WARP_BUILD_CACHE_ROOT` on Windows. Windows uses the typed helper for uncached structured checkouts now.
- Rendered UI changes or computer-use proof. This is a CLI and cache behavior change.
