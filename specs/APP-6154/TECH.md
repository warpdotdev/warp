# Factories in the Cloud Mode environment selector: technical specification
## Context
The product contract is in [PRODUCT.md](PRODUCT.md). This document specifies the server prerequisite, GUI implementation, and later TUI implementation.
- [`EnvironmentSelector` (cloud pane and handoff) at e7656eab3f](https://github.com/warpdotdev/warp/blob/e7656eab3f802ebcbb4f4430a63940a7febcff96/app/src/ai/blocklist/agent_view/agent_input_footer/environment_selector.rs#L38-L115) stores only an environment `SyncId`. It reads [`CloudEnvironmentCatalog` at e7656eab3f](https://github.com/warpdotdev/warp/blob/e7656eab3f802ebcbb4f4430a63940a7febcff96/app/src/ai/cloud_environments/catalog.rs#L25-L170), which projects environment GSOs from `CloudModel`.
- [`AmbientAgentViewModel::spawn_agent` at e7656eab3f](https://github.com/warpdotdev/warp/blob/e7656eab3f802ebcbb4f4430a63940a7febcff96/app/src/terminal/view/ambient_agent/model.rs#L1080-L1175) always sends `agent_identity_uid: None` and a snapshot with the current environment, model, harness, and worker host. [`HandoffComposeState` at e7656eab3f](https://github.com/warpdotdev/warp/blob/e7656eab3f802ebcbb4f4430a63940a7febcff96/app/src/terminal/input/handoff_compose.rs#L18-L110) and [`PendingHandoff` at e7656eab3f](https://github.com/warpdotdev/warp/blob/e7656eab3f802ebcbb4f4430a63940a7febcff96/app/src/ai/blocklist/handoff/pipeline.rs#L274-L367) also retain only environment IDs. The handoff's [`build_spawn_request` at e7656eab3f](https://github.com/warpdotdev/warp/blob/e7656eab3f802ebcbb4f4430a63940a7febcff96/app/src/ai/blocklist/handoff/pipeline.rs#L935-L1017) sets `agent_identity_uid: None`.
- [`CloudAgentSettings.last_selected_environment_id` at e7656eab3f](https://github.com/warpdotdev/warp/blob/e7656eab3f802ebcbb4f4430a63940a7febcff96/app/src/ai/cloud_agent_settings.rs#L71-L84) stores an untagged environment ID. It cannot store a Factory UID without a new tagged preference.
- [`GET /api/v1/factory` at 65a0e40e](https://github.com/warpdotdev/warp-server/blob/65a0e40e253efc9953fcb8bcc7fc00303dbfd156/router/handlers/public_api/factories.go#L202-L249) pages accessible `JSONFactory` objects. [`GET /api/v1/agent/identities?factory_uid=` at 65a0e40e](https://github.com/warpdotdev/warp-server/blob/65a0e40e253efc9953fcb8bcc7fc00303dbfd156/router/handlers/public_api/agent_identities.go#L472-L558) exposes a team's Factory agents. Neither endpoint provides an authoritative set of managed backing environment IDs.
- A file-managed Factory's managed backing UID is [`FactoryFileRegistration.ManagedEnvironmentUID` at 65a0e40e](https://github.com/warpdotdev/warp-server/blob/65a0e40e253efc9953fcb8bcc7fc00303dbfd156/model/types/factory_files.go#L103-L119). A live-managed Factory's auto-created provenance is [`FactoryConfig.DefaultEnvironmentAutoCreated` at 65a0e40e](https://github.com/warpdotdev/warp-server/blob/65a0e40e253efc9953fcb8bcc7fc00303dbfd156/model/types/factory.go#L54-L70). Replacing that default clears provenance; simply using an environment as a default does not make it managed.
- The Factory web composer passes its Foreman's UID as [`agent_identity_uid` at 65a0e40e](https://github.com/warpdotdev/warp-server/blob/65a0e40e253efc9953fcb8bcc7fc00303dbfd156/client/packages/factory/src/pages/NewRun/RunComposer.tsx#L185-L199). The server applies identity defaults before run preflight in [`TaskDispatcher.AddTask` at 65a0e40e](https://github.com/warpdotdev/warp-server/blob/65a0e40e253efc9953fcb8bcc7fc00303dbfd156/logic/ai/ambient_agents/add_task.go#L354-L405). The separate `POST /factory/{uid}/runs` route cannot replace Cloud Mode's interactive spawn, handoff snapshot, attachments, and conversation fork without enlarging its contract.
## Proposed changes
### Server prerequisite: an authoritative selector snapshot
Add an authenticated, team-scoped `GET /api/v1/factory/selector-options?team_uid=<uid>` response to `warp-server`. It is separate from the Factory web list; do not create Factory GSOs in Warp Drive. Register its static path before `/:uid` in `router/handlers/public_api/factories.go`; document its read schema in `public_api/openapi.yaml`. Its shape is:
```json
{
  "factories": [
    {
      "uid": "factory-uid",
      "team_uid": "team-uid",
      "name": "Factory name",
      "alias": "optional-alias",
      "default_environment_uid": "environment-uid",
      "foreman_agent_uid": "service-account-uid"
    }
  ],
  "managed_environment_uids": ["environment-uid"],
  "page_info": { "has_next_page": false, "next_cursor": null }
}
```
- Page Factory choices with the existing Factory cursor and limit, but make `managed_environment_uids` the complete authorized set for the requested team on every page. The client publishes no choices until it has fetched all pages with nonrepeating cursors; it deduplicates Factory UIDs. A malformed cursor, malformed response, or failed later page is an incomplete load, not an empty list.
- Include a Factory row only when the principal can view the Factory, its configured default environment exists, belongs to its team, is viewable by the principal, and exactly one launchable `FOREMAN` identity belongs to that Factory and team. Resolve both live-managed and file-managed Foremen; `logic.GetFactoryForeman` at `logic/factories.go:2289` resolves a projected file-managed Foreman only and cannot alone identify every live-managed Foreman. Do not choose a random duplicate. Treat inability to determine eligibility as an error or omit that Factory; never produce a row with an unknown identity.
- Derive managed UIDs independently of which Factory rows are launchable. Use active registration associations for file-managed Factories and `DefaultEnvironmentAutoCreated && DefaultEnvironment != nil` for live-managed Factories with no active file registration. Intersect with the requested team's environment objects that this principal can view. Do not infer management from the Factory default alone, its display name, or a deterministic UID. Remove a UID when the association is retired, the live default is replaced, or the environment is deleted.
- Keep the response scoped to one team. No cross-team records or inaccessible Factory metadata are returned. When Factory access is denied, return no Factory rows but still provide authorized managed-environment UIDs if the principal may use Cloud Mode; this read contract is not a grant to create Factory runs.
- Use the existing authenticated `POST /api/v1/agent/run` contract with the selected Foreman as `agent_identity_uid` and the selected default as `config.environment_id`; do not add `factory_uid` or a separate launch route. Existing run authorization and preflight remain in force. The client rechecks the selector snapshot before dispatch, but the run API does not atomically verify that the Factory still owns that Foreman or default environment. Deploy the selector route before enabling the GUI flag.
- Do not add Factory attribution to run storage or the task/read response. Existing viewers show the recorded run configuration; they cannot reliably identify a historical Factory after selection, and must not infer one from a currently available Factory with the same default environment.
### Shared client target model and fetch
Add a typed Factory-selector API call to `AIClient`/`ServerApi` in `app/src/server/server_api/ai.rs`, using the same authenticated team header and error parsing as `spawn_agent`. Add a singleton or team-keyed async selector catalog adjacent to `app/src/ai/cloud_environments/catalog.rs` that merges the completed Factory snapshot with `CloudEnvironmentCatalog` summaries. Keep `CloudEnvironmentCatalog` itself GSO-only so orchestration and unrelated pickers do not change.
- Represent an option as a tagged `Environment(SyncId)` or `Factory { uid, environment_uid: SyncId, foreman_agent_uid }`. The Factory UID, not the environment UID, is its selection key. Derive the visible ordinary-environment list by excluding `managed_environment_uids` *after* applying existing `environment_matches_scope` rules. A Factory whose own default is in that hidden set remains a Factory row.
- Invalidate/refetch on active team change, authentication change, explicit refresh, and when the selector reopens after a stale snapshot. Never display the previous team's snapshot during a transition. Treat fetch and pagination errors as retryable; keep only a verified, correctly scoped snapshot. Do not treat an incomplete page as “zero Factories.” The initial load blocks selection until the managed UID set is authoritative.
- Add a tagged, team-scoped last-choice preference in `app/src/ai/cloud_agent_settings.rs`. On first read without that preference, use the existing `last_selected_environment_id` and its current fallback order. After an ordinary environment choice, continue updating the legacy environment setting for existing consumers and store the tagged environment choice. After a Factory choice, store only the tagged Factory choice. If that saved Factory is absent when opening a **new** composer, fall back to a visible ordinary environment; do not silently select its backing environment or another Factory. Keep the separate orchestration default unchanged.
### GUI target state and dispatch
Update `app/src/ai/blocklist/agent_view/agent_input_footer/environment_selector.rs` to render and select tagged rows for both `CloudPane` and `Handoff`. Keep a Factory-specific badge or label within the existing menu style; disambiguate equal names. Keep “New environment” tied to environment management. Add Factory-specific selection telemetry; do not put a Factory UID in `CloudAgentTelemetryEvent::EnvironmentSelected`'s environment field.
- Store the tagged choice in `AmbientAgentViewModel` and `HandoffComposeState`, not only in the view. Clearing a Factory on team change, removal, loss of eligibility, or selection of an ordinary environment clears its Foreman with it. A composer that loses its active Factory selection enters an invalidated state and disables submission until the user explicitly selects a replacement; its ordinary default-selection logic must not run in that state. This differs from resolving a saved preference on a fresh composer. A task viewer may retain read-only run configuration even when its target is no longer selectable.
- In `AmbientAgentViewModel::spawn_agent` and the handoff `build_spawn_request`, a Factory choice yields `agent_identity_uid = foreman_agent_uid` and `config.environment_id = default_environment_uid`. Do not copy the user's model, harness, runner, or worker-host overrides into this config. Omit those fields so the server applies Foreman defaults; retain orthogonal snapshot/handoff flags and attachment behavior. Display “Factory defaults” in locked controls when the selector response does not supply resolved execution values; do not show stale user controls as the Factory's effective values. Disable or hide the model, harness, runner, and worker-host controls during Factory composition; restore their prior local choices after switching to an ordinary environment.
- Carry the tagged choice through `HandoffPrepareInput`, `PendingHandoff`, handoff presentation and restoration, and the final request's Foreman/default-environment fields. Extend validation beyond `valid_environment_ids` to reject a vanished Factory or changed default/Foreman before forking or uploading. Recheck immediately before the final spawn; the server does not validate that Factory relationship. Keep explicit Factory selection ahead of asynchronous working-directory suggestions. The existing cancellation and restoration path must preserve the source prompt and attachments on a failed Factory dispatch.
- Keep read-only viewer labeling separate from selectable rows. Use the existing recorded run configuration; do not infer a Factory badge from the current catalog or an environment UID, because the Factory can be deleted and an ordinary run can use the same default.
## Decisions and trade-offs
- A server-projected selector snapshot wins over client-side `GET /factory` plus one identities request per Factory. The latter reuses endpoints but cannot reliably identify managed backing environments, can expose partially loaded pages, and costs N+1 roster requests.
- `POST /agent/run` with the Foreman's `agent_identity_uid` wins over `POST /factory/{uid}/runs`. It preserves Cloud Mode's interactive and handoff contracts without extending the run API. This leaves a stale-selection race that client checks cannot close atomically and provides no persisted Factory attribution.
- A tagged preference wins over storing a Factory UID in `last_selected_environment_id`. The latter cannot distinguish types and would break callers expecting environment IDs.
- A separate merged selector projection wins over changing the shared environment catalog into a Factory catalog. It avoids changing orchestration cards and the first TUI PR indirectly.
## Assumptions
- Host is locked with the named controls so the server's Foreman/Factory worker-host default is not overridden.
- Initial load failure blocks new selections instead of rendering a possibly incomplete ordinary-environment list. This preserves the managed-environment hiding invariant.
- No computer-use proof is required. The requester did not opt in to UI exploration or video verification for spec drafting.
## Rollout and out of scope
- First, land the server selector contract and its tests. Second, land the GUI Cloud Mode and GUI handoff implementation behind the `cloud_mode_factory_selector` Cargo feature, which enables `FeatureFlag::CloudModeFactorySelector` but is not enabled by default or in `DOGFOOD_FLAGS`. Enable that flag only after the selector route is available in the target environment. Rollback disables the new GUI option without changing existing environment selection or runs.
- In a separate TUI PR, export the tagged selector catalog through `app/src/tui_export.rs`; update `crates/warp_tui/src/handoff/model.rs` and its selector block to apply the same choice and validation. The GUI PR must not alter TUI rendering. Do not broaden `app/src/ai/orchestration/snapshots.rs` or environment management pickers in either PR.
## Validation criteria
- `go test ./router/handlers/public_api ./logic` in `warp-server` covers Factory list authorization, live/file-managed Foremen, absent/duplicate Foremen, stale/defaultless Factories, active registration versus unrelated shared default, provenance-cleared replacement, and pagination. Add a named `TestFactorySelectorOptions` case to the public API package.
- `cargo nextest run -p warp ai::cloud_environments::catalog::tests` preserves the original environment catalog behavior. Add `factory_selector.rs` with a `tests` module and run `cargo nextest run -p warp ai::cloud_environments::factory_selector::tests` for mixed-row type identity, scope, managed-only hiding, duplicate names, complete-page gating, retry, saved-choice migration, and stale-selection invalidation.
- Add cases to `model_tests.rs` and `pipeline_tests.rs`; run `cargo nextest run -p warp terminal::view::ambient_agent::model::tests` and `cargo nextest run -p warp ai::blocklist::handoff::pipeline::tests` for regular spawn parity, Factory `agent_identity_uid`/environment contract, locked defaults, handoff restoration, explicit-selection precedence, and zero normal-run fallbacks on errors.
- `cargo check -p warp` and `./script/format` in `warp` pass in the GUI implementation PR. Confirm the GUI flag is disabled until the server prerequisite is deployed. Tests inspect the GUI selector model and menu state; no computer-use run, video, screenshot, or visual mock is required without requester opt-in.
- In the later TUI PR, `cargo nextest run -p warp_tui` covers the same Factory selection, filtering, handoff, and errors. Do not mark APP-6154 complete for both surfaces until that separate PR passes.
