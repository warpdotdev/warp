# Factories in the Cloud Mode environment selector
## Summary
Cloud Mode users can start a new run through a Factory from the existing environment dropdown. A Factory choice starts the run as that Factory's Foreman in the Factory's default environment. The menu does not show Factory-managed backing environments as ordinary environments. [APP-6154](https://linear.app/warpdotdev/issue/APP-6154/spec-include-factories-in-warp-terminal-cloud-mode-environment) records the request.
## Behavior
1. The GUI Cloud Mode composer and the `&` local-to-cloud handoff composer show one mixed dropdown of ordinary environments and available Factories. They do not show a second Factory selector. The menu retains its existing search, keyboard selection, focus behavior, selected checkmark, and “New environment” action.
2. Each Factory row says that it is a Factory. Its name remains visible. If two rows share a name, their type distinguishes an ordinary environment from a Factory; Factories with identical names in the active team show their alias, or their full UID when an alias is absent or duplicated. The selected chip identifies a Factory as a Factory.
3. A Factory appears only for the active team, when the signed-in user can view it and start a run with its Foreman. A Factory does not appear if its default environment is missing, deleted, inaccessible, or outside the Factory's team, or if its Foreman is missing, inaccessible, or ambiguous. A Factory with no default environment does not appear. The server applies its existing run permissions and preflight checks at creation, but does not validate the selected Factory against the request.
4. Only environments that are Factory-managed backing environments disappear as ordinary environment rows. This includes an active file-managed Factory's associated backing environment and a live-managed Factory's server-auto-created environment while it retains that provenance. An unrelated environment remains visible even when one or more Factories use it as their default.
5. Factory selection is one choice in the composer. It supplies the Factory's selected default environment and Foreman identity for a **new** run. The user cannot choose a different environment while that Factory is selected. Choosing an ordinary environment removes the Foreman identity. The server does not atomically confirm that the Factory still has those defaults at submission.
6. While a Factory is selected, model, harness, runner, and worker-host controls do not accept independent changes. The controls show “Factory defaults” when the selector has no resolved value to display; they do not show the user's stale choices. The run uses the effective Foreman/Factory defaults, including its configured secrets and other inherited agent settings. Selecting an ordinary environment restores the normal controls and their pre-Factory choices.
7. A new run started from a Factory row uses the existing Cloud Mode run flow, including prompt, attachments, progress, cancellation, session joining, and eligible follow-ups. The request supplies the Foreman identity and the Factory's selected default environment; it does not persist an explicit Factory identity on the run.
8. A `&` handoff to a Factory also retains its normal source-conversation fork, snapshot, cancellation, and prompt-restoration behavior. The Factory choice and Foreman identity survive the asynchronous preparation and are applied to the final spawn request. A late automatic environment suggestion cannot replace an explicit Factory choice.
9. A Factory choice persists with the same “last chosen option” behavior as today's environment choice. The next fresh composer in the same active team defaults to that Factory while it is available. Existing saved ordinary-environment choices remain valid. A Factory saved for another team is never selected in the current team; the selector uses its existing ordinary-environment fallback.
10. While Factory data or the managed-environment association is loading, the menu does not offer an unverified Factory or an unverified backing environment as a selectable ordinary environment. A failed load shows a retryable error instead of silently starting a personal run. Previously verified options may remain visible only if they still belong to the active team; a new team never reuses stale options from another team.
11. If a selected Factory becomes unavailable before submission, the menu clears that Factory choice and requires an explicit replacement; it does not auto-select an ordinary environment or start a run against its old environment without its Foreman. If the run API rejects the submission, the composer retains the prompt and attachments and shows the failure. Retrying re-resolves availability; it never falls back to a normal run.
12. A running or previously completed task remains viewable through the existing run API even if its Factory, Foreman, or backing environment later disappears. Its read-only environment reflects the available recorded run configuration, without inferring a Factory label from the current selector. Existing follow-ups do not re-select a Factory from the dropdown.
13. No Factory row appears for signed-out users or users outside Factory access. An inaccessible Factory's name, UID, Foreman, and existence are not disclosed through the selector. Ordinary personal and team environments retain their current scope rules.
14. The first implementation PR changes the GUI Cloud Mode composer and GUI local-to-cloud handoff only. A separate, later TUI implementation PR uses the same Factory eligibility, managed-environment filtering, run identity, and error behavior. Other environment pickers, including orchestration cards and environment management, retain their existing behavior in both PRs.
## Decisions
- Fetch Factories from the Factory service into the existing dropdown, rather than persisting them as Warp Drive objects. Direct fetch avoids a second persistence model. It needs an online load and explicit error state; Warp Drive could support offline browsing but increases synchronization and identity complexity.
- Model the choice as either a Factory or an environment, rather than two independent selections. An independent pair could represent a Factory with the wrong environment or Foreman.
- Hide only Factory-managed backing environments. Hiding every Factory default would remove normal, shared environments that remain useful outside a Factory.
- Lock execution controls to Factory defaults when a Factory is selected. Allowing the regular controls to override Foreman defaults would make “start through this Factory” ambiguous.
- Deliver GUI first and TUI in a separate PR. The TUI shares domain behavior but has a different selector and handoff presentation.
## Assumptions
- **Assumption:** “Unavailable” means that a Factory cannot be identified, viewed, and submitted with exactly one usable Foreman and a viewable default environment. A transient server-side run preflight failure is reported at submission rather than predicted by the menu.
- **Assumption:** Host selection is locked with model, harness, and runner. A host override can bypass the Foreman's worker-host default even when those other controls are locked.
- **Assumption:** An initial Factory metadata failure blocks a new selection until a retry succeeds. This favors correct hiding and identity over an environment-only fallback whose managed backing rows could be mistaken for ordinary environments.
- **Assumption:** The menu follows its existing visual style. No mock or computer-use verification was requested; the implementation tests will verify behavior without visual captures.
## Out of scope
- Changing Factory creation, Foreman configuration, environment management, or permissions policy.
- Changing unrelated environment pickers or converting Factories into Warp Drive objects.
- Implementing the TUI UI in the GUI implementation PR; the TUI follow-up is a separate PR.
