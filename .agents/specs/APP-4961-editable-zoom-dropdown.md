*Spec: Editable zoom dropdown (combobox) — preset values plus free-text entry with input validation*

== PRODUCT ==
*Summary:* Replace the Zoom setting's fixed-value dropdown with a reusable editable dropdown (combobox) that keeps the existing preset zoom values and also lets the user type a percentage directly, validated with the same conventions as the Appearance page's editor fields. The desired outcome is that a user can set any integer zoom percentage in the supported range, not just the fixed presets.
*Key design choices:* (1) Build a new generic reusable `EditableDropdown<A>` component rather than overloading the filter-only `FilterableDropdown`, so commit semantics stay separate from filter semantics. (2) Mirror the existing `EditorView` validation lifecycle exactly — error border via `themes::theme::Fill::error()`, commit on `Enter`/`Blurred`, revert to the saved value on `Escape`/invalid — matching the new-windows size editors. (3) Set the accepted custom-entry range to 50–350% (the full span of the existing presets) so every preset is also typeable and there is no "selectable but not typeable" gap; preserve all existing presets including 350%.
*Behavior* (numbered, testable invariants from the user's view):
1. The Zoom control renders an editable text field showing the current zoom level, plus a dropdown menu listing the existing fixed presets `50, 60, 70, 80, 90, 100, 110, 125, 150, 175, 200, 225, 250, 300, 350` (each labeled `"{n}%"`). It no longer renders a read-only closed dropdown.
2. Selecting a preset from the menu commits it immediately — it dispatches `SetZoomLevel(preset)`, updates `WindowSettings.zoom_level`, and applies the zoom factor — identical to today's behavior.
3. The user can focus the text field and type a numeric zoom percentage. On `Enter` or blur, a valid value commits (dispatches `SetZoomLevel(value)`, updates `WindowSettings.zoom_level`, and immediately applies the corresponding zoom factor).
4. A value is *valid* iff, after trimming ASCII whitespace and stripping an optional single trailing `%`, it parses as a base-10 `u16` and falls in the inclusive range `[50, 350]` (step 1; integer percentages only). Every existing preset is valid; arbitrary integers in `[50, 350]` (e.g. `115`, `142`, `300`) are also valid.
5. Invalid input — empty, non-numeric, fractional (e.g. `12.5`), out of range (`< 50` or `> 350`), or malformed (e.g. `50%%`, `ab`, `5 0`) — is visibly marked invalid with the editor-style error treatment (error border) and does **not** overwrite the last valid setting. On `Enter`/blur with invalid text, the field reverts to the current saved `zoom_level` value and re-focuses; on `Escape` the field reverts without committing.
6. The control reflects external zoom-setting changes (command palette, reset-to-default, preset selection, or any other writer to `WindowSettings.zoom_level`) by re-syncing the displayed text and the selected preset to the current value — no stale text or selection state.
7. The reusable `EditableDropdown<A>` is generic over the item action type and carries no `AppearancePageAction` coupling inside the component itself; this PR wires it only to the Zoom setting (no other settings are migrated).
8. The existing zoom-in and zoom-out keybindings continue to work after a custom value is committed, moving to the next higher or lower preset respectively (for example, 137% steps to 150% or 125%).

*Design alternatives* (per decision point with more than one reasonable approach):
- *Where the editable dropdown lives* — (a) new `EditableDropdown<A>` in `app/src/view_components/`, vs (b) extend `FilterableDropdown` to optionally commit typed values. Selected (a): `FilterableDropdown`'s editor is filter-only and its menu/selection model is built around filtering; bolting commit semantics onto it would conflate two behaviors and risk regressing its existing callers (font family, AI font family, etc.). A new component keeps the contract clean and is the approach the requester asked for ("create an editable dropdown component").
- *Who owns range validation* — (a) a widget-local parse+range helper, vs (b) add `ZoomLevel::MIN`/`MAX` + `validate()` and reuse them. Selected (b) plus a thin widget parse helper that trims/strips `%`: adding `MIN`/`MAX`/`validate` to `ZoomLevel` matches the established `BackgroundBlurRadius`/`BackgroundOpacity` pattern, centralizes the range, and gives the editor a single source of truth.
- *Accepted custom range* — (a) `50–350%` (the full preset span), vs (b) `50–300%` (the value named in GitHub issue #7793). Selected (a): aligning the custom range with the preset span makes every preset also typeable (no "selectable but not typeable" gap) and is the least-surprising, internally consistent behavior. The issue's `50–300%` reads as an approximate example; see *Open questions resolved* — this is surfaced for product confirmation.
- *Commit trigger* — (a) commit on `Enter` and `blur` (matching the new-windows size editors), vs (b) `Enter`-only. Selected (a): consistency with the adjacent Appearance editors and the ticket's "validation like the code editor" requirement.
- *Dropdown popup reuse* — (a) reuse the `Menu<DropdownAction>` popup machinery from `dropdown.rs` inside the new component, vs (b) build a fresh menu. Selected (a): preserves preset selection behavior, styling, overlay-layer handling, and keyboard semantics already proven across many settings dropdowns.

*Open questions resolved:*
- *Custom range:* `50–350%` (integer percentages, step 1). Chosen to match the existing preset span so every preset is also typeable and there is no selectable-but-not-typeable gap. The GitHub issue named `50–300%`; this spec deviates to `50–350%` for internal consistency. **Confirm with product** — if a hard `50–300%` cap is required (with `350%` remaining preset-only and `301–349` rejected), the validator's `MAX` is lowered to `300` and the spec revised; no structural change.
- *350% preset:* retained. No preset is removed, preserving existing behavior (no regression).
- *Step / fractional values:* step 1, integer percentages only. `ZoomLevel` is `u16` and `as_zoom_factor` divides by 100; fractional zoom (e.g. `12.5%`) is rejected as invalid.
- *Trailing `%` and whitespace:* the validator trims ASCII whitespace and strips an optional single trailing `%`, so both `175` and `175%` commit to 175%. Multiple `%`, leading/trailing junk, or interior whitespace are invalid.
- *Commit/revert triggers:* commit on `Enter` and `blur` when valid; revert to the saved value on `Escape` and on `Enter`/`blur` when invalid (re-focus). Matches the new-windows size editors.
- *Reusable component scope:* `EditableDropdown<A>` is introduced as reusable but wired only to Zoom in this PR; migrating other settings is explicitly out of scope.
- *Model for implementation:* the requester asked that the implementation run use model `gpt-5-6-sol-xhigh`; the foreman applies that at implementation dispatch (not a spec concern). Recorded here so it is not lost.
- *Reproduction:* triage attempted to launch the GUI (`./script/run`) and hit host OOM (`SIGKILL`, ~3.9 GiB, no swap) — an environment-mismatch non-repro, not evidence the feature exists. *Risks / blast radius:* Zoom is a top-level, frequently used Appearance setting; a regression in commit/apply breaks zoom for all users on every platform (`SupportedPlatforms::ALL`). Mitigations: unit tests for parse/validate/commit/revert and external re-sync; preserve the exact `SetZoomLevel`/`ResetZoomLevel` action handlers and `WindowSettingsChangedEvent::ZoomLevel` subscription so all existing writers (command palette, reset) keep working unchanged; reuse the proven `Menu<DropdownAction>` popup to preserve keyboard/menu behavior; keep editor focus/blur consistent with the page's `SettingsPageEvent::FocusModal` flow so tab/navigation is not trapped.
