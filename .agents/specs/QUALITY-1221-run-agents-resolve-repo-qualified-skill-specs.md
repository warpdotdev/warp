*Spec: run_agents resolves repo-qualified child skill specs (org/repo:path, repo:skill) in the orchestration runtime*

== PRODUCT ==
*Summary:* Today a `run_agents` dispatch whose `skills[].spec` is a repository-qualified reference (`org/repo:path/to/SKILL.md` or `repo:skill-name`) — the format the tool schema documents and `scripts/factory-dispatch` emits — fails per-child with "Failed to resolve child agent skills: <spec>" and only succeeds if the caller hand-edits the spec to an absolute filesystem path. This spec makes the `run_agents` orchestration runtime resolve repo-qualified specs the same way `warp agent run --skill` already does, so foreman/agent dispatch works with the natural payload and no absolute-path workaround.

*Key design choices:*
1. **Client-led resolution (Option A).** Wire the existing client resolver `resolve_skill_spec` (already used by `warp agent run --skill`, already handles `org/repo:path` and `repo:skill`) into the run_agents remote-child skill-resolution path. The parent client resolves the repo-qualified spec to a concrete `SKILL.md` and sends its *content* to the child via the existing `SpawnAgentRequest.runtime_skills` channel — exactly as absolute-path skills are sent today.
2. **No proto/API change.** The server already passes `skills[].spec` through verbatim as `api.SkillRef.Path`, and the parent client already sends resolved skill content to the child as base64 `api.Skill` payloads in `runtime_skills`. The fix is purely client-side in the `warp` repo; `warp-server` and `warp-proto-apis` are not touched.
3. **Fallback seam, no regression.** Resolution is added as a *fallback* after the existing `SkillManager::active_skill_by_reference` lookup, so absolute-path specs and bundled-skill IDs keep resolving through the unchanged fast path. Only when that lookup misses AND the spec parses as repo-qualified does the new path run.

*Behavior* (numbered, testable invariants from the consumer's view):
1. A `run_agents` call whose `skills[].spec` is `org/repo:path/to/SKILL.md` resolves the skill and launches the child with that skill active — no absolute-path workaround, no "Failed to resolve child agent skills" error.
2. A `run_agents` call whose `skills[].spec` is `repo:skill-name` (simple name, repo-qualified) resolves the skill by scanning that repo's skill directories in precedence order and launches the child with it active.
3. The factory foreman dispatch path (which emits `org/repo:path` specs via `scripts/factory-dispatch`) succeeds end-to-end on the first `run_agents` call using the payload the script emits, with no hand-editing.
4. A `run_agents` call whose `skills[].spec` is an absolute filesystem path to an already-active skill still resolves (no regression vs. today's working workaround).
5. A `run_agents` call whose `skills[].spec` is a bundled-skill ID still resolves (no regression).
6. A repo-qualified spec whose repository is not present in the parent agent environment produces a clear, actionable error naming the repository (not just the bare spec string).
7. A repo-qualified `repo:skill-name` spec that matches multiple skills across the repo's provider directories, and a spec whose found repository's `origin` org does not match the requested `org/repo`, each produce a clear, actionable error (ambiguity / org-mismatch) rather than a silent mis-resolution.
8. A genuinely missing skill (repo present, path/name does not exist) produces a clear "skill not found in repo" error.

How a run_agents child skill spec flows today (end-to-end trace, re-verified against current code):
- The LLM emits a `run_agents` tool call with `skills: [{ "spec": "warpdotdev/factory-agents:triage/.agents/skills/factory-triage/SKILL.md" }]`.
- Server passes the raw `Spec` through verbatim: `warp-server/logic/ai/multi_agent/utils/output/tool_call/shared/run_agents.go:38-53` (`skillRefsToProto`) stuffs `skillRef.Spec` into `api.SkillRef{Path: &path}` with no resolution (`:44-46`); `skillRefsFromProto` (`:55-69`) round-trips it back.
- Client converts the proto `Path` into a local path reference with no repo-qualification awareness: `warp/app/src/ai/agent/api/convert_from.rs:111-151` (`convert_run_agents`) → `warp/crates/ai/src/skills/conversion.rs:113-126` (`skill_reference_from_api_skill_ref`) → `skill_reference_for_path` (`:104-111`) → `SkillPathOrigin::location_for_path` (`:57-79`, normalizes slashes via `collapse_slashes`) → `SkillReference::Path(LocalOrRemotePath::Local(PathBuf::from(spec)))`. The colon-bearing repo-qualified string becomes a relative local path.
- The `SkillReference` vec flows unchanged: `RunAgentsRequest.skills` (`convert_from.rs:128-131`) → `warp/app/src/ai/blocklist/action_model/execute/run_agents.rs:740-754` (`run_agents_to_start_agent_mode` Remote arm sets `skill_references: run_skills.to_vec()`) → `StartAgentExecutionMode::Remote` → `warp/app/src/pane_group/pane/terminal_pane.rs:1535-1565` (`dispatch_start_agent_conversation` builds `RemoteChildLaunchConfig { skill_references, ... }`) → `warp/app/src/pane_group/pane/terminal_pane.rs:1870-1963` (`launch_remote_child`) → `prepare_remote_child_launch` at `:1917`.
- Runtime resolution misses and fails: `warp/app/src/ai/orchestration/remote_child.rs:300-323` (`resolve_runtime_skills`) calls `SkillManager::active_skill_by_reference` for each reference; `warp/app/src/ai/skills/skill_manager.rs:377-409` (`active_skill_by_reference_with_origin`) for `SkillReference::Path` does `self.skills_by_path.get(path)` (`:394`), keyed by real filesystem paths. The repo-qualified string is not in that map → `None` → `PrepareRemoteChildLaunchError::UnresolvedSkills` (`remote_child.rs:316-322`) → `user_message()` "Failed to resolve child agent skills: <spec>" (`:75-80`), surfaced at `terminal_pane.rs:1920`.
- An absolute filesystem path works only because the factory environment clones repos under a shared root and the parent `SkillManager` has the skill loaded under that absolute path (so `skills_by_path.get` hits). The child receives skill *content* inline: `remote_child.rs:312-314` base64-encodes `api::Skill::from(skill.clone())` (which carries `content` + descriptor, `conversion.rs:141-165`) into `SpawnAgentRequest.runtime_skills` (`warp/app/src/server/server_api/ai.rs:233-235`, "Base64-encoded `warp.multi_agent.v1.Skill` payloads to restore as runtime skills").

The existing client resolver that already does this correctly (used only by `warp agent run --skill` today):
- `warp/app/src/ai/skills/resolve_skill_spec.rs:126-137` — `resolve_skill_spec(spec: &SkillSpec, working_dir: &Path, ctx) -> Result<ResolvedSkill, ResolveSkillError>`. Returns `ResolvedSkill { skill_path, name, instructions, parsed_skill: ParsedSkill }` (`:30-37`); `ParsedSkill` carries `content`.
- `warp/crates/warp_cli/src/skill.rs:129-179` — `SkillSpec::from_str` parses `org/repo:path/to/SKILL.md` and `repo:skill-name` exactly (splits on the first `:`; qualifier `org/repo` or `repo`; `skill_identifier` may be a full path (`is_full_path`, `:94-99`) or a simple name).
- `resolve_skill_spec` dispatches to `resolve_repo_qualified` (`:206-276`) which finds candidate repo roots from `SkillManager::directories_with_skills()` (`skill_manager.rs:228-236`, keys are repo roots) filtered by `dir.file_name() == repo`, validates `org` against the repo's `origin` remote (`:236-260`), then `resolve_in_single_repo_root` (`:366-405`) → `resolve_from_root_path_by_directory_scan` (`:407-453`, full-path branch joins `repo_root + skill_identifier` and `parse_skill`s it; simple-name branch scans provider dirs in precedence). Errors: `NotFound`, `RepoNotFound`, `Ambiguous`, `OrgMismatch`, `ParseFailed` (`:83-108`).
- The sync `resolve_skill_spec` is purely local (cache + disk scan; no network). The async `clone_repo_for_skill` (`:145-204`) is invoked separately by the `warp agent run --skill` wrapper (`resolve_skill` in `warp/app/src/ai/agent_sdk/mod.rs`, `needs_clone = args.sandboxed && org.is_some() && repo.is_some()`) before calling the sync resolver — it is not called inside `resolve_skill_spec`.
- The parent cloud environment loads every cloned repo's skills: `SkillManager::set_cloud_environment(true)` + `is_cloud_environment` (`skill_manager.rs:54, 93-95`) makes all `directory_skills` entries in scope, so `directories_with_skills()` includes the factory-agents repo root in the foreman→child case.

*Design alternatives* (per decision point with more than one reasonable approach):

- **Where repo-qualified spec resolution lives — A (client-led) vs B (server-led) vs C (coordinated split).**
  - *A — client-led, reuse `resolve_skill_spec` (CHOSEN).* Reuses the existing, tested resolver; consistent with `warp agent run --skill`; no proto/API change (server already passes `Spec` through; parent already sends content via `runtime_skills`); no GitHub fetch on the dispatch hot path (parent cloud env has repos cloned → local cache/disk hit); child gets content inline so it need not have the repo. Best fit for the factory foreman→child case, which is the reported defect.
  - *B — server-led, reuse `ValidateAndNormalizeSkillSpec` (`warp-server/logic/ai/ambient_agents/skills/skill_validation.go`). REJECTED.* Requires a proto change to carry skill content (or a normalized child-env path) from server to child; adds GitHub-auth + content-fetch to the run_agents dispatch hot path (latency, new failure modes, principal/auth requirements); diverges from `warp agent run --skill` (two resolution code paths); the server resolver is currently used only for ambient-agent skill *registration*, a different flow.
  - *C — coordinated split (server validates/normalizes + client resolves content). REJECTED.* Most robust but most cross-cutting; needs a proto contract change and cross-repo coordination for marginal benefit over A. The factory case gains nothing from server-side access checks because the parent already holds the repos locally.
  - *Why A:* it is the smallest change that fixes the reported defect, reuses the most logic, introduces no proto/server change, and matches existing client behavior. The reported failure is specifically the parent-client dispatch path, which is exactly where A resolves.

- **Sync local-first vs async with clone fallback.**
  - *Sync, local-first (CHOSEN for v1).* Reuse the sync `resolve_skill_spec` (cache + disk scan) directly from the sync `resolve_runtime_skills`. Covers the factory case (parent has repos cloned). No async ripple through `prepare_remote_child_launch` → `launch_remote_child`. Lowest blast radius.
  - *Async with `clone_repo_for_skill` fallback (DEFERRED).* Would support a parent that lacks the repo locally by cloning `org/repo` on demand, matching `warp agent run --skill`'s sandboxed-mode behavior. Requires making `resolve_runtime_skills`/`prepare_remote_child_launch` async and restructuring `launch_remote_child` (`terminal_pane.rs:1917`) to await prep before spawning. Deferred: the factory parent always has the repos, adding a network `git clone` to the dispatch hot path is a separate, larger change that should be evaluated on its own (and carries auth/cost considerations for arbitrary public repos). Tracked as an explicit follow-up, not a v1 gate.

- **Error surface — enrich vs new variant.**
  - *Enrich `UnresolvedSkills` entries (CHOSEN).* Keep `PrepareRemoteChildLaunchError::UnresolvedSkills { references: Vec<String> }` (`remote_child.rs:66, 316-322`) but, for repo-qualified specs that fail resolution, make the `references` entry `"<spec> (<reason>)"` where `<reason>` is the `ResolveSkillError` rendering (e.g. "Repository 'factory-agents' not found locally", "Skill 'x' is ambiguous; specify as repo:skill_name"). `user_message()` then reads "Failed to resolve child agent skills: <spec> (<reason>)" — actionable, no enum change, stable contract.
  - *New variant `SkillResolutionFailed { spec, reason }` (REJECTED).* Cleaner typing but expands the public error enum and ripples to every match site; the enriched-string approach conveys the same actionable info with less churn.

*Proposed changes:*
1. **Resolution seam — `warp/app/src/ai/orchestration/remote_child.rs`.** In `resolve_runtime_skills` (`:300-323`), keep the existing `active_skill_by_reference` fast path unchanged. When it returns `None` for a `SkillReference::Path(LocalOrRemotePath::Local(path))`, attempt repo-qualified resolution: render the path string, parse it with `SkillSpec::from_str`; if it parses with a `repo` qualifier (i.e. it is repo-qualified, not a bare local path), call `resolve_skill_spec(&spec, working_dir, ctx)`. On `Ok(resolved)`, push `BASE64_STANDARD.encode(multi_agent_api::Skill::from(resolved.parsed_skill).encode_to_vec())` into `runtime_skills` — the same encoding used for fast-path skills (`:312-314`). On `Err(resolve_err)`, record the spec in the unresolved list with the enriched `"<spec> (<resolve_err>)"` entry. Non-repo-qualified strings that miss the fast path keep the existing behavior (bare spec in `references`). Bundled-skill IDs are unaffected (handled by the fast path). Extract the new logic into a small helper (e.g. `fn resolve_repo_qualified_skill(reference, working_dir, ctx) -> Option<Result<ParsedSkill, ResolveSkillError>>`) for testability.
2. **Thread `working_dir` into the seam.** Add a `working_dir: PathBuf` (or `Option<PathBuf>`) field to `RemoteChildLaunchConfig` (`remote_child.rs:29-41`) and pass it through `prepare_remote_child_launch` (`:147-233`) into `resolve_runtime_skills`. Source it at the call site `warp/app/src/pane_group/pane/terminal_pane.rs:1535-1565` (`dispatch_start_agent_conversation`) from the parent run's working directory / the pane's cwd (the same cwd context the orchestration runtime already has access to via `ctx`); default to the process cwd or an empty path when unavailable (the `directories_with_skills()` fast path inside `resolve_skill_spec` does not require `working_dir` when the manager already knows the repo — `working_dir` is only the fallback for an unknown repo, per `resolve_repo_qualified` `:221-227`). Also update the other `RemoteChildLaunchConfig`/`prepare_remote_child_launch` caller (`warp/app/src/ai/agent_sdk/ambient.rs`) and the test builder (`remote_child_tests.rs:12-25`) to supply the new field.
3. **No server/proto change.** `warp-server` `skillRefsToProto`/`skillRefsFromProto` and `api.SkillRef` are unchanged. `SpawnAgentRequest.runtime_skills` is unchanged. `SkillReference` and `LocalOrRemotePath` are unchanged (no new variant).

*Open questions resolved:*
- *Is the server-side `remote` block over-fielding (foreman fabricating `runner_id`) in scope?* No. That is a foreman-prompting/guidance issue (`RunAgentsRemoteParams` exposing optional fields is by design — the server resolves defaults when omitted), not a `warp` code defect. It is out of scope for this change; the factory-foreman skill already carries separate guidance to leave `runner_id`/`harness`/`worker_host` unset. This spec fixes only the skill-spec resolution.
- *Does the fix need the async clone fallback?* No for v1. The factory parent always has the repos cloned (`is_cloud_environment`), so the sync local resolver suffices. Clone fallback is an explicit deferred follow-up (see Design alternatives).
- *What `working_dir` does the run_agents path use?* The parent run's working directory (the cloud environment's repo root / pane cwd), threaded via `RemoteChildLaunchConfig`. It is only a fallback inside `resolve_skill_spec` for repos the `SkillManager` does not yet know; in the factory case the manager already knows the repo, so `working_dir` is not on the critical path.
- *Could a repo-qualified string be misread as a local path (e.g. colons on Windows)?* The new path parses the string as a `SkillSpec` *before* any filesystem interpretation, and only runs when the fast path already missed, so existing absolute-path/bundled-id resolution is untouched. `SkillSpec::from_str` is the single parser reused from `warp agent run --skill`, keeping semantics identical.
- *Should ambiguity/org-mismatch errors block or warn?* Block (fail the launch with an actionable error), matching `resolve_skill_spec`'s existing semantics and the run_agents contract that any unresolved skill fails the whole launch (`remote_child.rs:316-322`).

*Risks / blast radius:*
- The run_agents remote-child launch path is on the orchestration hot path; the new logic is a fallback that only runs when the existing lookup misses, so the common absolute-path/bundled-id cases are unchanged. Risk is confined to repo-qualified specs (the previously-failing case), so a regression here can only affect specs that already failed.
- `resolve_skill_spec` reads the `SkillManager` cache and (on miss) the local filesystem via `parse_skill`; in the cloud factory environment the cache is warm (`is_cloud_environment`), so no unexpected disk walks on the hot path.
- Adding a `working_dir` field to `RemoteChildLaunchConfig` touches every constructor (two callers + tests); all must be updated to compile.
- Headless/backend change (orchestration runtime, no UI): per `factory-verification`, no `computer_use`/visual proof is required — verification is the regression test plus warp's documented checks.
