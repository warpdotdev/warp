*Spec: Precise setup-command updates in the Oz CLI (warp repo)*

== PRODUCT ==

*Summary:* Extend `oz environment update` so users can (1) insert a setup command at a specific index preserving existing order, (2) edit one setup command by index without resending the unchanged full list, and (3) clear-and-rebuild the setup-command list — while preserving the existing append (`--setup-command`/`-c`) and text-based remove (`--remove-setup-command`) flags for backward compatibility.

*Key design choices:*
- **Zero-based indexes**, aligned to warp-server's binding contract (the contract authority). Insert index is in `0..=len` (insert at `len` appends); edit index is in `0..=len-1`.
- **Position-based addressing for insert/edit** eliminates the duplicate-command ambiguity that text-based removal suffers from; duplicate command text is allowed (setup commands may repeat), addressed by index.
- **No new wire transport for the CLI**: the CLI keeps its existing read-modify-write of the full `AmbientAgentEnvironment` model through `UpdateManager.update_object` (the Warp Drive `upsertCloudEnvironment` full-list upsert) — this is the documented equivalent per the warp-server spec. Insert/edit/clear are computed **client-side** on the local clone of the model, then the full model is pushed exactly as today.
- **Client-side validation mirrors the server's shared limits** (enforced server-side on the upsert): each command non-empty after trim, ≤4096 runes/command, ≤100 commands total. The CLI validates before sending so the user gets a fast, clear error instead of a server rejection.
- **Display numbering becomes zero-based** so the index a user types matches the number they see in `oz environment get`/update output (user-facing change — see *Open questions resolved* / *Risks*).

*Behavior* (numbered, testable invariants from the user's view):
1. `oz environment update <id> --insert-setup-command <index> <command>` inserts `<command>` at the zero-based `<index>`, shifting all commands at that index and later down by one; all existing commands and their relative order are preserved.
2. Insert at index `N` (where `N` is the current setup-command count) appends to the end. Insert at a negative number, a non-integer, or any index `> N` is rejected with a clear error naming the valid range `0..=N`.
3. `oz environment update <id> --edit-setup-command <index> <command>` replaces the command at the zero-based `<index>` with `<command>` and leaves every other command untouched. Edit at a negative number, a non-integer, or any index `>= N` is rejected with a clear error naming the valid range `0..=N-1`.
4. `oz environment update <id> --clear-setup-commands` empties the setup-command list. `oz environment update <id> --clear-setup-commands --setup-command "a" --setup-command "b"` rebuilds the list to exactly `["a", "b"]` in the given append order (deterministic).
5. Multiple `--insert-setup-command` occurrences in one invocation are applied in command-line order; multiple `--edit-setup-command` occurrences are applied in command-line order. (Each new index-mode flag is mutually exclusive with the other modes and with append/remove, except `--clear-setup-commands` may combine with `--setup-command` for rebuild — see *Behavior* 8.)
6. Existing `--setup-command`/`-c` (append) and `--remove-setup-command` (remove first exact-text match, warn if absent) behave exactly as before; commands that combine them (legacy append+remove) still parse and apply.
7. Conflicting setup-command operation flags are rejected at parse time (clap `conflicts_with`), so a user never gets a silently surprising result from mixing modes: `--insert-setup-command` conflicts with `--setup-command`, `--remove-setup-command`, `--edit-setup-command`, and `--clear-setup-commands`; `--edit-setup-command` conflicts with `--setup-command`, `--remove-setup-command`, `--insert-setup-command`, and `--clear-setup-commands`; `--clear-setup-commands` conflicts with `--remove-setup-command`, `--insert-setup-command`, and `--edit-setup-command` (but NOT `--setup-command`, to enable rebuild).
8. The only allowed multi-mode setup-command combinations are: `--setup-command` + `--remove-setup-command` (legacy), and `--clear-setup-commands` + `--setup-command` (rebuild). When `--clear-setup-commands` + `--setup-command` are combined, the list is cleared first, then the appended commands are pushed in order.
9. After a successful update, the printed environment details number setup commands zero-based (the display changes from the prior 1-based numbering so the index the user just used remains visible and consistent for the next edit).
10. Out-of-range / non-integer / negative index errors are surfaced as fatal, user-facing errors (via the existing `report_fatal_error` path) before any server update is attempted; no partial mutation is sent to the server on a validation failure. This mirrors the server contract (non-integer/negative index → 400-equivalent, out-of-range → 404-equivalent) at the CLI layer, since the CLI resolves indexes client-side.
11. Each setup command (after trim) must be non-empty, ≤4096 runes, and the total command count must be ≤100; violating any of these (on append, insert, edit, or rebuild) is a fatal, user-facing error before any server update is attempted, mirroring the server-side upsert validation.

*Design alternatives:*
- **Index base (0- vs 1-based)** — warp-server (the designated contract authority) committed its spec with **binding zero-based** indexes; the CLI aligns to that contract. Tradeoff: the existing `print_environment_details` display is 1-based today, so aligning the CLI to 0-based also changes the user-facing display numbering to 0-based (so the index a user types matches what they see). The alternative — keep a 1-based display with 0-based edit indexes — was rejected as confusing/inconsistent. The display change is a user-facing surface change flagged for requester confirmation (see *Open questions resolved* / *Risks*).
- **Insert at end** — options: (a) a separate `--append`/reuse `--setup-command`, (b) reject insert at `len`, (c) permit insert at `len` as append. Chose (c): `Vec::insert(len, x)` already appends, so permitting `len` makes `--insert-setup-command` a full positioning primitive and avoids a special-case error. Rejecting `len` would push users to mix `--insert-setup-command` with `--setup-command`, which we then have to forbid (Behavior 7).
- **Duplicate-command addressing** — options: (a) address edits/removals by text (ambiguous when duplicated), (b) address by index. Chose (b) for the new edit op: index uniquely identifies the slot, so duplicates are never ambiguous. The existing text-based `--remove-setup-command` keeps its first-match behavior (preserved for compat); duplicate-text removal ambiguity is a pre-existing, accepted limitation out of scope for this change.
- **Where the mutation logic lives** — options: (a) inline in `update_environment_after_auth_check` (async, `ModelContext`-bound, hard to unit-test without the heavy app build), (b) extracted pure functions in the `warp_cli` crate (fast to test — triage confirmed `cargo test -p warp_cli environment_` builds and passes). Chose (b): pure helpers in `crates/warp_cli/src/environment.rs`, unit-tested in `lib_tests.rs`. The app crate only wires them into the read-modify-write flow. This follows the existing `validate_description` precedent (a pure helper already in the CLI crate, `environment.rs:9-19`) and keeps the regression tests off the slow app build.
- **Flag shape for insert/edit** — options: (a) two tokens `--insert-setup-command <index> <command>` (the ticket's stated shape), (b) a delimited single token `--insert-setup-command <index>:<command>`. Chose (a) per the ticket. With clap `num_args = 2` + `ArgAction::Append`, values are collected as a flat `Vec<String>` of pairs (`[idx, cmd, idx, cmd, …]`); a pure helper chunks them into `(usize, String)` pairs. Multi-word commands must be shell-quoted (same constraint as today's `--setup-command "pip install foo"`).
- **Per-invocation mode exclusivity** — options: (a) allow arbitrary mixing of insert/edit/append/remove/clear with a defined application order, (b) make the new index modes mutually exclusive with each other and with legacy flags (only clear+append excepted). Chose (b): mixing insert (which shifts indexes) with edit/remove-by-index in one call makes the second index ambiguous; rejecting those combos at parse time is safer and simpler than documenting shifting-index semantics. Legacy append+remove stays allowed.
- **Where to enforce the shared validation limits** — options: (a) only server-side (let the upsert reject), (b) mirror client-side too. Chose (b): mirror non-empty-after-trim / ≤4096 runes / ≤100 commands in the pure helper so the CLI fails fast with a clear message before the round-trip, matching the server-side upsert validation the warp-server spec defines.

*Risks / blast radius:*
- **Display change (user-facing)**: switching `print_environment_details` from 1-based to 0-based changes the visible numbering in `oz environment get` and the update success output for all users, not just the new flags. This is deliberate (so typed 0-based indexes match displayed numbers) but is the widest blast radius of the change; flagged for requester confirmation. Mitigation: it is a display-only change (no data migration, no model change); if rejected, fall back to documenting the index/display base difference (see *Open questions resolved*).
- **Read-modify-write race**: between the CLI reading the current model and pushing the update, another client could change `setup_commands`, making an index point at a different command than the user intended. This is a pre-existing property of the whole `environment update` flow (it already clones, mutates, and pushes with a `revision`); the new index ops inherit it unchanged. Mitigation: the existing `revision` optimistic-concurrency reject on stale writes remains; users re-run. No new concurrency risk is introduced.
- **Backward compatibility**: adding fields to `EnvironmentCommand::Update` is safe (only `run()` destructures it; tests use `..`). Existing `--setup-command`/`--remove-setup-command` parsing and behavior are untouched. The new conflicts only forbid combinations that did not previously work anyway. The validation limits (non-empty/≤4096/≤100) are already enforced server-side on the upsert, so mirroring them client-side only fails invalid input earlier — it does not reject any input the server would have accepted.
- **`num_args = 2` parsing**: a user who forgets to quote a multi-word command (e.g. `--insert-setup-command 1 pip install foo`) gets a parse error because clap consumes exactly two values. This matches today's `--setup-command` quoting requirement; document it in the flag help.
- **App-build pressure for verification**: the regression tests live in the fast `warp_cli` crate by design; the app-crate change is a thin wiring call + a one-line display change validated by `cargo build`/CI. If CI cannot build the app in the sandbox, the `warp_cli` tests still prove the parse + mutation + validation logic.
