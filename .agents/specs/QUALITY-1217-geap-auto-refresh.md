*Spec: Auto-refresh expired Gemini Enterprise (GEAP) credentials for interactive agents instead of surfacing an error*

== PRODUCT ==

*Summary:* For BYOLLM Gemini Enterprise interactive agents, when a user returns after their GEAP access token has expired and prompts the agent to continue, the Warp client today sends the stale (expired) token, Google rejects it, and the client surfaces an "expired or invalid credentials" error with an inline manual-refresh button. The desired change is for the client to detect the expired credential transparently, refresh it automatically before the request is sent, and proceed without surfacing the error — while keeping the manual-refresh recovery UI as the fallback for terminal refresh failures and bounding refresh/retry so it can never loop forever.

*Key design choices:*
1. **Mirror the existing Grok "await-refresh-before-send" pattern** already in `ResponseStream::spawn_request` rather than inventing a new mechanism. Grok already blocks a request on a single-flight OAuth refresh (bounded by a 5s timeout) and injects the fresh token into `params.api_keys` before `spawn_generate`, surfacing a terminal non-recoverable error on failure. GEAP gets the same shape: block-before-send on hard expiry, inject the fresh `google_cloud_credentials`, surface the existing manual-refresh error on failure.
2. **Block only on hard expiry, not on the proactive lead window.** A new `GeapCredentials::is_expired()` (past hard expiry, no lead time — the twin of `GrokTokens::is_expired()`) gates the blocking pre-send refresh. The existing proactive timer + the asynchronous safety net already handle the near-expiry 5-minute lead window; blocking every near-expiry request would add latency to requests the proactive path already covers. The reported scenario ("user returns after the token expired") is exactly the hard-expiry case.
3. **Bounded single refresh per request, single-flight across concurrent prompts.** At most one pre-send refresh per request; concurrent GEAP requests join the same in-flight mint (strict single-flight, like Grok's `grok_refresh_waiters`); a failed/timed-out refresh is terminal for that request (non-recoverable, no auto-retry). A subsequent Google 401 on the freshly-minted token is NOT auto-refreshed again — it falls through to the existing `InvalidApiKey(GeminiEnterprise)` → manual-refresh error mapping. This is the infinite-loop guard.

*Behavior* (numbered, testable invariants from the user's view):
1. **Happy path — expired token, refresh succeeds:** A user returns after their GEAP token has expired and sends a continuation prompt. The client refreshes the access token automatically and sends the request with the new token. The user sees the agent continue working; no "expired or invalid credentials" banner and no manual-refresh button appears.
2. **No friction on valid tokens:** When the stored GEAP token is still valid (not at/past hard expiry), the request is sent immediately with the current token; no blocking refresh, no extra latency.
3. **Concurrent prompts coalesce:** Two GEAP requests that arrive while the token is expired share a single mint; both proceed with the same freshly-minted token once it completes. Only one mint runs at a time.
4. **Refresh-failure fallback:** If the automatic refresh fails (Google STS/IAM error, network error, or the bounded wait times out), the client does NOT send the request with the dead token. It surfaces the existing Gemini Enterprise credentials recovery UI (the manual "Refresh credentials" / "Manage" buttons), so the user can recover manually. This is a terminal failure for that request — no automatic retry of the refresh.
5. **Bounded loop — no infinite refresh:** A single request triggers at most one automatic refresh. If the refreshed token is itself rejected by Google (a 401 on the retried send), the client surfaces the manual-refresh error UI; it does not refresh again. A persistently-failing mint cannot spin a hot refresh loop (single-flight + bounded timeout + terminal-on-failure).
6. **First mint unaffected:** When no GEAP token has been minted yet (first use, or after a sign-in/config change), the existing behavior is unchanged: the request carries no `google_cloud_credentials` and the asynchronous mint proceeds as today; this spec adds no blocking wait for a first mint.
7. **Non-GEAP requests unaffected:** Requests whose model provider is not GeminiEnterprise (BYO Anthropic/OpenAI/Google/OpenRouter keys, Grok subscription, AWS Bedrock, custom endpoints) are unchanged — including the existing Grok request-time refresh, which is untouched.
8. **Proactive refresh intact:** The existing proactive timer (refresh 5 min before expiry, floored at 60s) and the asynchronous safety net (`refresh_geap_credentials_if_needed`) keep running unchanged; the blocking pre-send refresh is additive and only fires on hard expiry at request time.

*Design alternatives* (per decision point with more than one reasonable approach):

- **When to refresh: await-known-hard-expiry-before-send (chosen) vs. retry-only-on-401 vs. combine both.**
  - *Await-known-hard-expiry-before-send (chosen):* detect hard expiry before send, block on a single-flight refresh, inject the fresh token, send once. Pros: matches the established Grok pattern in the exact same function; avoids sending a known-dead token (no wasted round-trip, no server-side 401 log); one code path; minimal new state. Cons: does not help if the token expires mid-request or has an unknown expiry (GEAP always sets `expires_at: Some` on both DirectWif and ServiceAccount legs at `app/src/ai/geap_credentials.rs:465`/`514`, so unknown-expiry does not occur in practice).
  - *Retry-only-on-401:* send the stale token, and on a server `InvalidApiKey(GeminiEnterprise)` re-mint and re-send once. Pros: catches mid-request expiry. Cons: requires interpreting a terminal stream-finished error as a retry trigger (the current `recovery_action` mapping treats InvalidApiKey as non-recoverable and surfaces the manual UI), re-sends a request that may have already started server-side work, and risks the infinite loop the requester explicitly wants avoided; no existing client-side 401→refresh→retry machinery to reuse.
  - *Combine both:* await-before-send AND retry-on-401. Cons: two refresh code paths, higher loop risk, more state; marginal benefit since GEAP always carries a known expiry.
  - **Selected: await-known-hard-expiry-before-send.** It is the codebase's existing pattern for the sibling BYO OAuth credential, it directly fixes the reported scenario, and it is the simplest design that satisfies the "no infinite loop" requirement. The mid-request-expiry edge is already bounded by the 5-min proactive lead window + the proactive timer; a token that expires between the expiry check and the send is the same race Grok accepts today.

- **Where the GEAP single-flight coordinator state lives: mirror Grok's split (chosen) vs. app-layer-only.**
  - *Mirror Grok's split (chosen):* put `GeapRefreshOutcome`, the `geap_refresh_waiters` field, and the eligibility/begin methods on `ApiKeyManager` in `crates/ai` (where `grok_refresh_waiters`/`GrokRefreshOutcome`/`begin_expired_grok_refresh` live); reuse the existing app-layer mint kickoff (`refresh_geap_credentials_with_options`) and wake the waiters from `apply_geap_mint_result`. Pros: structural parity with Grok, the shared state lives on the singleton the response stream already updates, the network/policy code stays where it is. Cons: the waiter-wake call site (`apply_geap_mint_result`) is in the app layer and must call back into the crates/ai coordinator (a small cross-layer seam, same as Grok's `spawn_grok_refresh` waking waiters).
  - *App-layer-only:* put everything in `app/src/ai/geap_credentials.rs`. Cons: diverges from the Grok structure and duplicates the single-flight coordinator rather than reusing the established shape.
  - **Selected: mirror Grok's split.**

- **Failure surfacing: new terminal `AIApiError` variant (chosen) vs. reuse `GeminiEnterpriseCredentialsExpiredOrInvalid` directly.**
  - *New terminal variant (chosen):* add `AIApiError::GeminiEnterpriseCredentialsRefreshFailed` (non-recoverable, `is_actionable=false`) mirroring `GrokSubscriptionTokenRefreshFailed`, and map it in `RenderableAIError::From` to the existing `GeminiEnterpriseCredentialsExpiredOrInvalid` so the existing `GeminiEnterpriseCredentialsErrorView` (manual refresh button) renders. Pros: distinguishes "auto-refresh failed" from "Google rejected a sent token" in telemetry/crash reporting while reusing the existing recovery UI; matches the Grok precedent.
  - *Reuse the existing renderable directly:* emit `GeminiEnterpriseCredentialsExpiredOrInvalid` without a new `AIApiError` variant. Cons: loses the failure-cause signal in crash reporting; the response stream emits `AIApiError` (not `RenderableAIError`), so a new `AIApiError` variant is needed anyway for a clean emission path.
  - **Selected: new terminal `AIApiError` variant mapped to the existing renderable/UI.**
