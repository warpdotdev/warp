*Spec: Headless non-interactive agent run in Warp Agent CLI*

== PRODUCT ==

*Summary:* Add a one-shot `warp run` subcommand to the standalone Warp Agent CLI/TUI binary. It accepts an instruction from a positional argument, piped stdin, or both; obtains explicit consent for its V0 auto-approval policy; runs Warp's built-in Oz agent without mounting the interactive TUI; prints an interactive-TUI resume hint when the conversation starts; and provides script-safe text or JSON Lines output. The implementation must reuse the app crate's in-process agent runner while preserving the TUI's authentication, settings, execution-profile, persistence, and indexing behavior.

*Key design choices:*
- `warp run [PROMPT]` is a new subcommand of the standalone TUI binary, not an alias for the separate Oz CLI's `warp agent run` command and not a subprocess invocation of another Warp binary.
- V0 runs approval-eligible agent actions in the existing `RunToCompletion` autoexecute mode after explicit up-front consent. A terminal invocation asks once; a piped or otherwise non-TTY invocation must pass `--yes`. Hard denials, protected paths, and organization policy remain authoritative, and the command never falls back to an in-run prompt.
- Headless runs use the existing `AgentSource::Cli` wire value. A new TUI-specific source is deferred because it would require coordinated server schema, API, generated-client, telemetry, and UI changes outside this single-repository V0.
- Default output follows the script-friendly Codex contract: startup/progress/diagnostics, including the resume hint, go to stderr while stdout contains only the final assistant response. `--output-format jsonl` exposes the existing agent event stream as a machine-readable protocol with a terminal event.

*Behavior*:
1. The installed standalone Warp Agent CLI accepts:
   - `warp run [--yes] [--profile <ID>] [--output-format <text|jsonl>] [PROMPT]`
   - The existing global `--api-key <KEY>` / `WARP_API_KEY` authentication option remains available before or after `run`.
   - `text` is the default output format. No shorthand or compatibility form for `warp agent run` is added.
2. Prompt input is resolved before app initialization:
   - With a non-empty positional `PROMPT` and terminal stdin, the positional value is the prompt.
   - With no positional value and piped stdin, the complete UTF-8 stdin value is the prompt.
   - With both a positional value and piped stdin, the positional value is the instruction and stdin is additional context. The model-visible string is the positional value, two newline characters, then stdin, preserving each non-empty source's contents.
   - An absent or whitespace-only effective prompt, unreadable stdin, or non-UTF-8 stdin is a usage/input error. It must not start an agent or mount the TUI.
   - Piped stdin is limited to 10 MiB. Exceeding the limit fails clearly and nonzero instead of buffering unbounded input.
   - When stdin supplies prompt/context or is otherwise not a terminal, the command cannot consume it for confirmation; `--yes` is therefore required before app initialization. A non-TTY invocation without `--yes` fails with an actionable usage error and produces no agent output.
3. `run` is strictly headless and one-shot. It initializes the shared app model graph, starts one local Oz conversation in the process's current working directory, waits for its terminal status, and exits. It never enters alternate-screen mode, reads interactive keystrokes after startup consent, or mounts `RootTuiView`. As soon as the server conversation token is assigned, it prints exactly one `Resume in the interactive TUI: warp --resume <TOKEN>` hint to stderr; accepting a resume token in `warp run` remains out of scope.
4. Authentication remains TUI-scoped:
   - The run uses `--api-key`, `WARP_API_KEY`, or already-persisted Warp Agent CLI credentials from the TUI secure-storage namespace.
   - Missing, expired, or invalid credentials fail on stderr and with a nonzero status. The headless command never starts device login, opens a browser, or waits for interactive authentication.
5. Agent configuration remains TUI-scoped:
   - With no `--profile`, the TUI default execution profile supplies the model, allowlists/denylists, and other hard policy inputs.
   - `--profile <ID>` selects an existing file-backed TUI execution profile by stable ID. An unknown ID is an error; it must not fall back to another profile.
   - The V0 run-to-completion override auto-approves approval-eligible actions after startup consent; it does not erase organization-enforced restrictions, command denylists, protected-path rules, or other non-overridable hard denials.
   - v1 does not expose separate model, MCP, skill, environment, harness, conversation, cwd, or share flags from the Oz CLI. `--yes` only acknowledges the fixed V0 auto-approval policy; it does not select a different permission mode.
6. Permission handling uses explicit startup consent followed by no in-run prompts:
   - With terminal stdin and no `--yes`, the command writes `Start a headless agent run? Approval-eligible agent actions will run automatically; hard safety and organization restrictions still apply. [y/N]` to stderr and reads exactly one confirmation response before app initialization. Only case-insensitive `y` or `yes` proceeds; empty input, EOF, or any other answer exits nonzero without starting an agent.
   - `--yes` skips the question and constitutes explicit consent for both terminal and unattended invocations. The warning remains documented in `--help`; the flag must not weaken any hard denial.
   - After consent, the new conversation starts with the existing `AIConversationAutoexecuteMode::RunToCompletion` override. Approval-eligible commands, file operations, MCP actions, and other supported actions do not pause for per-action approval.
   - Explicit command denylists, protected write paths, organization-enforced restrictions, unsupported actions, and any other hard denial still transition the run to a blocked terminal result with a useful action/reason description.
   - `AskUserQuestion` cannot be auto-answered and transitions the one-shot run to `Blocked`. A blocked run never waits on stdin, launches the TUI, or opens a second confirmation prompt.
7. Default `text` output is pipeline-safe:
   - stdout contains only the final assistant-authored text, in message order, followed by one newline. It excludes reasoning, conversation/run IDs, tool calls and results, TODOs, progress, diagnostics, and log paths.
   - The startup consent question/warning, the exactly-once interactive-TUI resume hint, human-readable progress, and tool activity may stream to stderr. Errors and blocked reasons are reported on stderr.
   - A successful response with no assistant text produces empty stdout rather than substituting progress or metadata.
8. `jsonl` output is a streaming protocol:
   - Every stdout line is one complete JSON object. Existing stable agent/tool/system event representations are reused rather than exposing internal Rust types.
   - stderr is reserved for out-of-protocol startup consent, the exactly-once interactive-TUI resume hint, and diagnostics; no human-readable progress is mixed into stdout.
   - Once app initialization begins, stdout ends with exactly one system terminal event: `run_completed`, `run_blocked`, `run_cancelled`, or `run_failed`. A successful terminal event contains the complete final assistant text; blocked/failed events contain a stable reason string. Pre-initialization argument, stdin, or authentication-bootstrap failures may produce no JSONL records and are reported on stderr.
9. Exit status is zero only when the one-shot agent conversation reaches successful completion. Argument/input failures, authentication failures, unknown profiles, permission-blocked runs, cancellations, agent errors, and app/driver failures exit nonzero. Signal termination retains the platform's normal signal-derived exit behavior; the command must never convert interruption into success.
10. The headless command preserves the existing TUI launch identity:
    - It continues to use `LaunchMode::Tui`, `ExecutionMode::Tui`, TUI settings, TUI persistence, TUI execution profiles, the `.tui` secure-storage service suffix, and the TUI logging frontend.
    - It assigns `AgentSource::Cli` only for the headless TUI entrypoint. Interactive TUI launches continue to use `None`.
    - `None` today means `ServerApi` omits the `x-oz-agent-source` value entirely, so requests cannot be attributed or filtered as a CLI-originated run. Reusing the already-supported `CLI` wire value makes the new programmatic entrypoint observable without changing its TUI settings/storage identity.
    - Codebase indexing remains disabled for the TUI because persisted-index restore and snapshot writes are not safe across concurrent GUI/TUI processes. Project/global rules and skills discovery continue through the non-index-backed context paths already initialized for the TUI.
11. Existing modes remain compatible. A bare `warp`, `warp --resume <TOKEN>`, provider API-key maintenance flags, `--help`, `--version`, and worker re-exec dispatch retain their current behavior. `run` conflicts structurally with interactive/resume and provider-key maintenance modes rather than attempting to compose with them.
12. v1 deliberately excludes session resume or follow-up turns, detached/background execution, interactive fallback, cloud runs, third-party harnesses, full Oz CLI flag parity, a GUI monitor, codebase indexing, and bundling/shelling out to the Oz CLI.

*Design alternatives*:
- *Binary boundary:* Invoking or bundling the Oz CLI would reuse its command parser but violates the standalone TUI binary boundary, complicates distribution, and forks TUI settings/auth identity. Reimplementing an agent loop in `warp_tui` would duplicate critical lifecycle logic. Selected: add a narrow TUI-facing app API that constructs the existing local Oz run in-process and delegates to `agent_sdk` / `AgentDriver`.
- *Command shape:* A root `--headless`/`--print` flag is close to Claude Code but composes ambiguously with `--resume` and maintenance flags. `warp agent run` mirrors the separate Oz CLI but exposes the wrong product hierarchy and invites unsupported flag parity. Selected: the explicit `warp run` subcommand requested by the product owner.
- *Permission policy:* The original proposal followed Claude Code's `dontAsk` and Codex's explicit-sandbox precedent: use the TUI profile and fail closed when an approval would be required. That is safest for unattended execution, but it makes V0 much less useful and conflicts with the product decision to default headless runs to auto-approval. Selected: after explicit per-invocation consent, set the existing conversation-level `RunToCompletion` override while retaining hard denials and organization restrictions. A TTY asks once; non-TTY/piped use requires `--yes` because an interactive question would consume prompt input or hang automation. This deliberately diverges from the conservative precedent without silently escalating.
- *Output contract:* Reusing the current SDK stdout stream unchanged makes shell pipelines consume progress and tool results rather than the answer. A single final JSON document is easy to parse but provides no progress for long runs. Selected: final-only stdout plus stderr progress by default, with an opt-in JSONL event stream. Expose `--output-format` rather than a `--json` boolean so the values are self-describing and extensible.
- *Prompt and stdin:* Requiring exactly one source is simple but prevents the established “instruction plus piped context” workflow. Treating concatenated bytes as one opaque prompt makes ordering unclear. Selected: positional instruction first, then two newlines, then piped context, matching documented Codex semantics and making tests deterministic.
- *Launch identity, source, and indexing:* Reclassifying the whole run as `LaunchMode::CommandLine` would turn on GUI settings/persistence and indexing, violating the TUI boundary. Keeping `AgentSource::None` preserves current interactive TUI behavior but omits source attribution on API requests. A new `Tui`/`HeadlessTui` source would be the most specific taxonomy, but it expands this single-repo V0 into a coordinated server/database/OpenAPI/generated-client/web-UI rollout. Selected: keep `LaunchMode::Tui` and all of its storage/settings/indexing behavior, but return the already-supported `AgentSource::Cli` for the typed headless entrypoint only; interactive TUI remains `None`.
- *Resume hint placement:* Omitting the hint preserves a minimal stream but makes a newly created conversation hard to recover. Printing it on stdout would corrupt final-only text and JSONL consumers. Selected: reuse the existing exactly-once conversation-token lifecycle seam and print `warp --resume <TOKEN>` to stderr as startup information. This is a small output-routing addition; headless resume remains out of scope.

*Risks / blast radius:*
- Refactoring driver output can change the established Oz CLI protocol. Mitigation: make the sink/output policy explicit per caller, preserve the current Oz CLI policy unchanged, and add byte-for-byte tests for both existing and TUI-specific routes.
- Auto-approval is intentionally broader than the original fail-closed proposal. Accidentally bypassing a command denylist, protected path, organization restriction, or unsupported-action guard would be a security regression. Mitigation: use the existing invocation-scoped `RunToCompletion` mechanism rather than rewriting profiles, preserve hard-denial ordering, require explicit startup consent, and add representative plus exhaustive permission coverage.
- Permission or question prompts can occur through commands, file edits/reads, MCP tools, terminal writes, computer use, and `AskUserQuestion`. Missing one can hang CI. Mitigation: centralize “interactive approver available” in the execution context and test that every post-start action either autoexecutes or reaches a terminal blocked result without reading stdin.
- Initialization currently treats all TUI logs as file-only because interactive rendering owns stdout/stderr. Headless output needs stderr without allowing ordinary logs to corrupt it. Mitigation: keep logs file-backed and write only intentional progress/diagnostics through the output sink.
- Extending `TuiEntryPoint` affects provider-key maintenance and interactive auth. Mitigation: preserve typed entrypoints, add launch-mode tests for API-key extraction and storage identity, and keep all existing TUI session tests.
- Input buffering can consume excessive memory or block on a terminal. Mitigation: read only non-terminal stdin, enforce the 10 MiB cap while reading, and fail before full app bootstrap.
- Reusing `AgentSource::Cli` groups the headless TUI command with the Oz CLI in source filters, so it does not distinguish the two products. That is an accepted V0 tradeoff; a distinct source requires a coordinated multi-repo compatibility rollout.
